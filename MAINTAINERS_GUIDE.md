# Maintaining the COS Volleyball website

The site is a framework-free web app: HTML is in `website/index.html`, CSS in `website/styles.css`, and JavaScript in `website/app.js`. Only the **contents of `website/`** are deployed to https://cosvolleyball.github.io/.

## Quick file map

| File | Purpose |
|---|---|
| `website/index.html` | Forms, labels, navigation, organizer dashboard and dialog markup |
| `website/styles.css` | Theme, desktop/mobile layouts, focus and touch styling |
| `website/app.js` | Public event listing, registration, calendar export, waitlist and organizer interactions |
| `website/` image/icon files | Hero image, favicon and Apple touch icon |
| `tests/regression.cjs` | Isolated JS regression suite using fake Supabase responses |
| `.github/workflows/deploy.yml` | Tests and publishes `website/` from `main` |
| `.github/workflows/pr-regression.yml` | Runs tests on pull requests |
| `BACKLOG.md` | Authoritative pending-work record |

**Backend:** Supabase provides organizer authentication, private event and registration data, RPC functions and Row Level Security. Email delivery uses a separate Supabase Edge Function and Google Apps Script process. Phase 10's waitlist promotion Cron job runs outside GitHub Pages. Website-only edits should not change or recreate those services.

## Small content changes

- Theme colors: edit `:root` in `website/styles.css`.
- Headings/help text: edit `website/index.html`. Keep existing element IDs in sync with references in JavaScript.
- Event defaults: the editor fields in `website/index.html` and `clearEditor()` in `website/app.js` should agree. The normal defaults are 6 PM, a blank date, three-hour duration, Hillside Community Center, $5 and 24 spots.
- Payment choices: `#payment-method` in `index.html`. Current new-registration choices are Venmo and cash; older records can have other methods.
- Registration confirmation text: the signup handler in `app.js`. The **actual email message** is generated by the separate email services, not this website.
- Duplicate Event: `openDuplicateEventEditor()` copies settings only; never copy IDs, private links, registrations, payments or attendance, and keep the new date blank and status Draft.
- Add to Calendar: `googleCalendarLink()` and `createIcsCalendar()` use actual UTC start/end times. Do not include private tokens or player data in exported calendar details.
- Existing JavaScript helpers to locate: `loadEvents()`, `eventCard()`, `eventDetailPage()`, `loadEventRoster()`, `loadInvitedEvent()`, `openSignup()`, `loadManageRegistration()`, `loadAdminEvents()`, `refreshAdmin()`.

## Safe development and deployment

1. Make changes in a feature branch. Prefer a pull request rather than pushing directly to `main`.
2. From `tests/`, run `npm ci --ignore-scripts` and `npm test` with Node 24 or newer. Tests use fake backend responses, not live data.
3. If useful, serve `website/` locally with `cd website && python3 -m http.server 8000`, then visit `http://localhost:8000`. Local pages cannot fully test organizer login without the live backend.
4. Review the [test checklist](TEST_CHECKLIST.md). The CI test suite does not test actual screen layout, iPhone/Android behavior or OS calendar imports.
5. Confirm the pull-request test workflow passes, then merge into `main`.
6. In GitHub **Actions**, confirm **Deploy Colorado Springs Pickup Volleyball** reports success. The GitHub Pages workflow publishes `website/` only.
7. Reopen https://cosvolleyball.github.io/ and spot-check the changed public behavior. For organizer-only behavior, use an authorized account and controlled test records.

If a deploy run uploads the site but fails to find a `github-pages` artifact, prefer **Actions → Deploy Colorado Springs Pickup Volleyball → Run workflow → main** to start a fresh run. Re-running the same failed run can create duplicate artifacts.

## Security and privacy

- The GitHub repository is public: **never** store service-role keys, passwords, database exports, Gmail bridge credentials, `EMAIL_BRIDGE_TOKEN`, or private player contact information.
- The browser Supabase publishable key is not a secret; RLS and server-side functions must enforce access.
- Private `?invite=` and `?manage=` links are bearer credentials. Do not log, export, or put them in calendar entries, screenshots or public issues.
- Public rosters show player names/status, not personal emails or phone numbers.
- Do not edit live registrations, payment history, email delivery or Supabase schema as part of unrelated frontend cleanup.
- Backend database changes must be reviewed and applied separately in Supabase, not committed as SQL into this public repo.

## Troubleshooting and recovery

- **Site hasn't updated:** check the newest green deployment for `main`, then reload without cache.
- **No events:** check browser console/network and Supabase availability. Do not paste private tokens into issue reports.
- **Registration problem:** inspect the displayed error and the server RPC behavior; do not re-register real players to test a hypothesis.
- **Email absent:** check Spam/Junk and the separate worker/queue through authorized admin tools. Registration and email delivery are distinct systems.
- **Bad update:** use GitHub's **Revert** feature on the relevant commit or merge PR, then allow GitHub Actions to redeploy. Do **not** delete/reset Supabase tables or rerun old migrations as a frontend rollback.
- **Broken deploy:** the previous successful Pages deployment may remain live, but verify that rather than assuming. A failed upload/publication is not proof that the website code is broken.

Keep rollback instructions limited to the current GitHub Actions setup. The old repository-root deployment and one-off SQL migrations are no longer active installation procedures.
